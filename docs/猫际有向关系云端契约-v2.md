# Cat-AI 猫际有向关系云端契约 v2

## 1. 状态与适用范围

本文冻结 Cat-AI 在 CloudBase 环境 `cloud1-d6gpjpxunc74669d7` 中的猫际有向关系 v2 契约，适用于：

- 云函数 `catOnlineV2` 的 `listCommunityInsights` 与 `castRelationshipVote`；
- 集合 `ci_relationship_edges` 与 `ci_relationship_votes`；
- 小程序页面 `pages/community-insights/`；
- 同猫身份撤销、关系边复核和本地只读管理台。

外层云函数请求仍使用 `schemaVersion: 1`；`directionVersion: 2` 是关系子域版本，二者不能混用。只有代码、索引、权限、函数部署和真机验收全部完成后，产品才可显示“有向关系云端已启用”。

本文是 v2 的唯一规范来源。其他文档、测试夹具或历史数据与本文冲突时，以本文为准，并通过显式迁移修正，不能在客户端猜测。

## 2. 两类关系必须分离

Cat-AI 同时存在两种用途不同的数据，禁止自动互转：

| 数据 | 作用域 | 语义 | 当前存储 |
| --- | --- | --- | --- |
| 私有角色卡 `privateRoleCard` | 单设备、单用户 | 主人确认的朋友、室友、母亲、孩子、照护者等身份或角色 | 微信本机 `catai_mini_relationships_v1`，内部 `schemaVersion=2` |
| 社区观察边 `communityObservationEdge` | 邀请制小屋、多成员 | 成员对某一箭头方向上可观察互动的独立投票 | CloudBase `ci_relationship_edges` / `ci_relationship_votes` |

私有角色卡可以表达经资料确认的亲子或照护身份；社区观察边只表达持续观察到的互动，不能证明血缘、固定地位、疾病或“性格”。本地角色卡不得自动上传为社区投票，社区多数票也不得覆盖本地角色卡。

## 3. 有向语义

一条 v2 边由有序端点 `(communityId, fromCatId, toCatId)` 唯一确定：

```text
A → B  !=  B → A
```

- `fromCatId`：箭头起点、当前观察的角色主体；
- `toCatId`：箭头终点、当前观察的关系对象；
- 同一对猫可以同时存在 `A → B` 和 `B → A` 两条边；
- 保存 v2 边时绝不能对两个端点排序；
- 不能把两个方向合并计票，也不能把一个方向的旧票复制到另一个方向。

v2 观察选项固定为 `RELATION_CHOICES_V1`：

| choice | 页面标签 | 起点角色 | 终点角色 | 观察边界 |
| --- | --- | --- | --- | --- |
| `bonded` | 主动亲近 | 主动亲近方 | 亲近对象 | 起点持续主动靠近、依偎或梳毛 |
| `playmate` | 发起玩耍 | 玩耍发起方 | 玩耍回应方 | 起点发起游戏，终点回应且互动可自然停止 |
| `housemate` | 平静共处 | 平静共处方 | 共处伙伴 | 从起点视角可与终点平静共享空间 |
| `needs_space` | 需要空间 | 需要空间方 | 相处对象 | 起点持续回避、哈气或需要分区观察 |
| `unsure` | 暂时看不准 | 观察发起方 | 观察对象 | 当前方向的证据不足 |

这些角色是一次社区观察中的方向说明，不是猫咪永久身份。角色词表变化必须发布新的选择契约版本，不能在相同 `choice` 下静默改变含义。

## 4. 规范猫身份

所有新 v2 边必须引用当前小屋内的规范 `catId`，不得用昵称、图片名或本机 `localPetId` 作为端点。服务端写入前必须：

1. 按 `ci_user_pet_links.catId` 与 `ci_cat_identities.canonicalCatId` 解析到规范身份；
2. 验证两个身份属于同一 `communityId` 且状态允许参与关系；
3. 拒绝缺失、跨小屋、撤销中、已停用或规范链循环的身份；
4. 在规范化后再次确认 `fromCatId !== toCatId`。

若身份合并使现有边两端变成同一个规范猫，禁止继续作为活动边展示或计票；该边必须进入 `needs_review`，并保留审计原因。身份撤销期间，`catIdentity` 继续使用兼容端点 `catAId/catBId` 把相关活动边标记为 `needs_review`。

## 5. `ci_relationship_edges` 字段契约

v2 活动边必须包含：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `_id` | string | `drel_` 前缀的服务端确定性 ID；客户端不得指定 |
| `communityId` | string | 边所属小屋 |
| `relationshipContractId` | string | 固定为 `cat-ai.relationship.directed` |
| `relationshipContractVersion` | number | 固定为 `2` |
| `directionVersion` | number | 固定为 `2` |
| `directionState` | string | 正常 v2 固定为 `directed` |
| `directionKey` | string | 服务端生成，固定为 `fromCatId::toCatId`；客户端不得提交 |
| `fromCatId` | string | 规范化后的箭头起点 |
| `toCatId` | string | 规范化后的箭头终点，必须不同于起点 |
| `fromCat` | object | 安全展示投影 `{ catId, displayName }`；以 ID 为准，名称只是缓存 |
| `toCat` | object | 安全展示投影 `{ catId, displayName }`；以 ID 为准，名称只是缓存 |
| `catAId` | string | 兼容字段，v2 必须等于 `fromCatId` |
| `catBId` | string | 兼容字段，v2 必须等于 `toCatId` |
| `catA` | object | 兼容投影，v2 必须与 `fromCat` 同一身份 |
| `catB` | object | 兼容投影，v2 必须与 `toCat` 同一身份 |
| `voteCounts` | object | 五个固定 choice 的非负整数计数，不能含客户端提交的聚合值 |
| `totalVotes` | number | 必须等于五个 `voteCounts` 之和 |
| `state` | string | `active`、`needs_review` 或终态；只有 `active` 可投票 |
| `createdAt` | ISO string | 首次创建时间，改票不得覆盖 |
| `updatedAt` | ISO string | 最近一次有效写入时间 |

边 ID 的逻辑作用域为：

```text
directed-relationship-v2 | communityId | fromCatId | toCatId
```

客户端读取时，服务端应使用当前猫身份重建 `fromCat/toCat` 名称，避免档案改名后长期显示旧快照。浏览器端不得把名称当作关联键。

## 6. `ci_relationship_votes` 字段契约

每位活动成员对每条有向边最多一条当前票：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `_id` | string | `drvote_` 前缀的服务端确定性 ID |
| `edgeId` | string | 对应 v2 边 ID |
| `communityId` | string | 必须与边一致 |
| `directionVersion` | number | 固定为 `2` |
| `fromCatId` | string | 必须与边一致 |
| `toCatId` | string | 必须与边一致 |
| `ownerKey` | string | 由可信 OpenID 经服务端 HMAC 生成，不返回客户端 |
| `membershipId` | string | 提交时的活动成员关系 |
| `choice` | string | 只能是 `RELATION_CHOICES_V1` 中的值 |
| `evidenceSightingIds` | array | v2 首次上线阶段固定为空数组，见第 10 节 |
| `idempotencyKey` | string | 8–128 位受限字符；同键异参必须冲突 |
| `requestHash` | string | 服务端对规范请求体计算的 SHA-256 |
| `createdAt` | ISO string | 首次投票时间 |
| `updatedAt` | ISO string | 最近改票时间 |

票 ID 的逻辑作用域为：

```text
directed-relationship-vote | edgeId | ownerKey
```

客户端不得提交 `ownerKey`、`membershipId`、边 ID、票 ID、聚合计数或角色标签。

## 7. 写入不变量与事务

`castRelationshipVote` 必须在服务端执行以下约束：

1. 可信 OpenID 已映射为用户，成员关系仍为 `active`；
2. `directionVersion === 2`；缺失或旧版本返回 `LEGACY_RELATIONSHIP_READ_ONLY`；
3. 两个端点经规范化后存在、同小屋、不同且可用；
4. 服务端按规范端点生成 `directionKey=fromCatId::toCatId`，并保证 v2 兼容字段严格满足 `catAId=fromCatId`、`catBId=toCatId`；
5. 当前票、旧计数、新计数和边状态在同一数据库事务内读取并写入；
6. 首次投票只增加新 choice；改票先将旧 choice 减一，再将新 choice 加一；
7. 重放相同幂等键和相同请求返回已有结果，不重复计数；
8. 相同幂等键配不同请求返回 `IDEMPOTENCY_CONFLICT`；
9. 任一计数不得为负数，提交后的 `totalVotes` 必须等于已知 choice 计数之和；
10. `needs_review`、身份撤销中或端点已失效的边不得继续投票。

如检测到孤儿票、计数不一致、未知 choice、缺失端点或规范化自环，应失败关闭并交给管理台复核，不能在客户端静默修复。

## 8. 唯一索引与查询索引

CloudBase 必须使用下列关系索引：

| 集合 | 字段 | 类型 | 名称 |
| --- | --- | --- | --- |
| `ci_relationship_edges` | `communityId, directionKey` | 联合唯一 | `uniq_relationship_direction_key` |
| `ci_relationship_edges` | `communityId, state` | 组合 | `idx_relationship_state` |
| `ci_relationship_edges` | `communityId, state, catAId` | 组合 | `idx_relationship_active_cat_a` |
| `ci_relationship_edges` | `communityId, state, catBId` | 组合 | `idx_relationship_active_cat_b` |
| `ci_relationship_votes` | `communityId, edgeId, ownerKey` | 联合唯一 | `uniq_relationship_voter` |
| `ci_relationship_votes` | `communityId, ownerKey` | 组合 | `idx_relationship_owner` |

`directionKey` 是所有关系边都必须具有的服务端字段：

- v2 固定为 `fromCatId::toCatId`，因此 `A → B` 与 `B → A` 分别唯一；
- legacy 固定为 `legacy::<edgeId>`，每条历史边都有独立且非空的键，不会占用任何 v2 方向；
- `directionKey` 只负责唯一性，v2 仍必须保持 `catAId=fromCatId`、`catBId=toCatId`，以便 `catIdentity` 通过兼容端点查找身份依赖边。

旧索引 `uniq_relationship_pair(communityId, catAId, catBId)` 必须在启用 v2 写入前迁移；否则 v1 边可能阻塞其中一个 v2 方向。迁移必须先为每条现存边回填非空 `directionKey`，再创建 `uniq_relationship_direction_key(communityId, directionKey)`，验证成功后才删除旧唯一索引。索引迁移前必须统计、备份并校验重复键，不能只修改文档或函数代码。

## 9. 盲投与安全响应

成员端执行“先投后看”：

- 当前成员未对某条 v2 边投票时，返回 `distributionVisible: false`、`voteCounts: null`、`myChoice: ''`、`roleLabels: null`；
- `totalVotes` 可以作为参与量返回，但不得返回任何 choice 的占比、领先项或角色结论；
- 当前成员投票后，才返回该边的完整五项聚合计数和本人的当前 choice；
- owner、admin、reviewer 在成员端同样遵守盲投，不获得例外；
- 管理审核若未来需要查看完整分布，应使用独立的受审计管理接口，不能复用成员接口绕过盲投。

聚合并列时必须显示“意见并列”，不得按照 choice 枚举顺序伪造领先项。零票显示“尚无有效投票”。

响应不得包含 OpenID、`ownerKey`、`membershipId`、其他成员的单票、精确位置、原始 fileID、embedding、HMAC 密钥或内部阈值。

## 10. 证据目击暂未开放

v2 首次上线阶段，客户端必须提交：

```json
{ "evidenceSightingIds": [] }
```

原因是当前单猫目击流程没有稳定生成“同一张已审核目击同时包含两只规范猫”的 `observedCatIds` 契约，页面也没有证据选择器。非空证据列表应明确返回“功能未开放”的稳定错误，不能接受无法验证的目击，也不能在文档中宣称证据附件已经可用。

未来开放前至少完成：

1. 多猫目击的录入、审核和 `observedCatIds` 规范化；
2. 证据必须已审核、同小屋并同时包含当前两个规范端点；
3. 身份合并或撤销后重建证据引用；
4. 页面提供可理解的证据选择和撤回入口；
5. 权限、并发和隐私回归测试。

## 11. v1 只读兼容

v1 边只保存排序后的 `catAId/catBId`，原始箭头方向不可恢复。服务端读取 v1 时必须返回：

```json
{
  "directionVersion": 1,
  "directionState": "legacy_pending",
  "fromCat": null,
  "toCat": null,
  "voteCounts": null,
  "distributionVisible": false,
  "myChoice": ""
}
```

兼容规则：

- v1 边及其票只读；
- 不把 v1 的 `catAId/catBId` 排序结果解释为方向；
- 不把旧计数复制给新 v2 边；
- 用户重新选择箭头并投票时创建独立 v2 边；
- v1 边使用 `directionKey=legacy::<edgeId>`，可继续显示“方向待确认”，但不能占用或阻止 v2 唯一键；
- 删除或归档 v1 数据需要单独的数据保留决策和审计，不随 v2 部署自动删除。

## 12. 列表完整性、分页与截断

`listCommunityInsights` 不得把固定 `limit(100)` 的结果冒充完整数据。猫、关系边、本人投票和地图目击必须分别采用以下一种策略：

1. 提供稳定排序与游标分页；或
2. 在一次性响应中提供明确的截断标志。

未实现游标前，`policy` 至少返回：

```json
{
  "relationshipDirectionVersion": 2,
  "relationshipChoiceVersion": 1,
  "blindBeforeVote": true,
  "catsTruncated": false,
  "relationshipsTruncated": false,
  "myVotesTruncated": false,
  "mapTruncated": false
}
```

特别是 `myVotes` 不能静默截断：否则服务端会把已经投票的成员误判为未投，错误隐藏其合法可见的分布。若无法完整读取本人票，应返回可重试错误或分页状态，而不是降级成“未投票”。

### 13.1 投票请求

```json
{
  "action": "castRelationshipVote",
  "schemaVersion": 1,
  "requestId": "request-token",
  "idempotencyKey": "relationship_vote-token",
  "communityId": "com_xxx",
  "directionVersion": 2,
  "fromCatId": "cat_a",
  "toCatId": "cat_b",
  "choice": "bonded",
  "evidenceSightingIds": []
}
```

### 13.2 已投票响应中的关系投影

```json
{
  "relationshipId": "drel_xxx",
  "communityId": "com_xxx",
  "directionVersion": 2,
  "directionState": "directed",
  "fromCat": { "catId": "cat_a", "displayName": "奶糖" },
  "toCat": { "catId": "cat_b", "displayName": "豆包" },
  "totalVotes": 2,
  "voteCounts": {
    "bonded": 1,
    "playmate": 1,
    "housemate": 0,
    "needs_space": 0,
    "unsure": 0
  },
  "distributionVisible": true,
  "myChoice": "bonded",
  "roleLabels": { "from": "主动亲近方", "to": "亲近对象" },
  "updatedAt": "2026-08-29T00:00:00.000Z"

```

`listCommunityInsights.policy.relationshipDirectionVersion` 不是装饰字段：前端只有在它严格等于 `2` 时才允许写入。健康检查也应暴露相同的关系契约版本，以便部署探针在无需成员数据的情况下发现旧函数。

## 14. 部署与迁移顺序

目标环境：`cloud1-d6gpjpxunc74669d7`。

1. 冻结旧关系写入窗口，确认客户端只调用 `catOnlineV2`；
2. 统计 v1/v2 边、票、重复键、孤儿端点、计数不一致和规范化自环；
3. 备份 `ci_relationship_edges` 与 `ci_relationship_votes`；
4. 若存在 v1 数据，保留其原始字段并标记只读语义，禁止推断方向；
5. 为全部现存边回填 `directionKey`：v2 使用 `fromCatId::toCatId`，legacy 使用 `legacy::<edgeId>`；
6. 创建第 8 节的 `uniq_relationship_direction_key`，确认所有文档已进入索引且无重复后删除旧唯一索引 `uniq_relationship_pair`，并核对另外五个关系索引；
7. 部署包含本契约校验的 `catOnlineV2`；
8. 调用 `health`，确认运行时、环境和关系契约版本；
9. 在真实微信登录态完成第 15 节验收；
10. 验收通过后上传对应小程序版本，并继续禁止旧 `catOnline` 客户端调用。

索引和函数部署是两个独立步骤。任一步失败都必须保持前端只读，不允许带着旧唯一索引开启 v2 写入。

## 15. 上线验收

至少使用同一小屋中的两只规范猫和两个真实微信用户验证：

1. A 用户对 `猫甲 → 猫乙` 投 `bonded`，只生成一条对应方向边和一条个人票；
2. B 用户投票前看不到 `猫甲 → 猫乙` 的 choice 分布，即使 B 是 reviewer；
3. B 投票后能看到正确聚合，A 的单票身份仍不可见；
4. A 重放相同幂等请求 10 次，总票数不增加；
5. A 改票后旧项减一、新项加一，总票数不变；
6. 对 `猫乙 → 猫甲` 投票会生成另一条边，两个方向独立统计；
7. 同票时页面显示“意见并列”，不伪造领先项；
8. v1 卡片仍显示“方向待确认”，旧请求写入返回 `LEGACY_RELATIONSHIP_READ_ONLY`；
9. 身份撤销中、跨小屋、同一规范猫两端和 `needs_review` 边均拒绝投票；
10. 猫咪改名后，列表显示当前名称而不是永久使用边内旧快照；
11. 人为触发猫、边或本人票读取上限时，响应给出分页或准确的截断状态；
12. 非空 `evidenceSightingIds` 在功能开放前被稳定拒绝；
13. 网络响应和日志不含 OpenID、ownerKey、其他成员单票、Key、精确位置、fileID 或 embedding；
14. 所有关系边都有非空 `directionKey`；`ci_relationship_edges.totalVotes` 与五项计数之和一致，且不存在重复 `(communityId, directionKey)`；
15. 本机私有角色卡未被自动上传、覆盖或根据云端多数票改变。

通过以上验收后，才能把 `relationshipDirectionVersion=2` 视为真实可用能力，而不是仅存在于本地源码中的声明。
