# 微信小程序制作流程与 Cat-AI 迁移方案

调研日期：2026-08-22  
适用项目：Cat-AI 猫咪识别、知识库与档案管理

> 本文基于微信开放文档入口、微信公众平台、腾讯云官方文档、工信部/中国政府网及网信办公开文件整理。微信后台入口、服务类目、接口能力和审核规则可能调整，提交前必须以当日微信公众平台显示为准。

## 1. 执行摘要

微信小程序从立项到上线的主流程是：

```text
确定主体与业务边界
  → 注册小程序并取得 AppID
  → 配置名称、类目、人员权限
  → 完成小程序备案与必要资质
  → 设计前后端和数据安全方案
  → 使用微信开发者工具开发
  → 配置隐私指引和服务器域名
  → 开发版、体验版、真机测试
  → 上传代码并提交微信审核
  → 审核通过后发布
  → 监控、灰度、迭代与合规维护
```

对 Cat-AI 的结论：

- 可行性：高，约 8/10。
- 不应直接把现有 HTML/JavaScript WebView 页面打包成小程序。
- 不应把 MiniMax、Kimi 或其他供应商 API Key 编译进小程序。
- 推荐采用“原生微信小程序 + 安全后端/云托管 + 数据库 + 对象存储”。
- 现有 FastAPI 的识别、知识检索和档案业务逻辑可以复用约 50%～70%，前端需要重新实现。
- 当前后端没有用户鉴权，所有宠物共用 `data/pets.json`，不能直接暴露给小程序用户。
- 猫咪照片、档案、健康备注属于需要谨慎处理的用户数据，必须落实最小收集、授权说明、用户隔离、删除和留存策略。
- 个体猫识别的 89 MB ONNX 模型不建议放入小程序代码包；应在服务端推理，或完成单独的模型下载与兼容性研究后再评估。

## 3. 前期决策

### 3.1 确定主体

常见主体包括：

- 个人；
- 个体工商户；
- 企业；
- 政府、媒体、其他组织。

选择原则：

- 如果要长期运营、接入支付、团队协作、品牌认证或商业化，优先企业或个体工商户主体。
- 个人主体能选择的服务类目和商业能力通常更有限。
- 主体、产品名称、隐私政策签署方、备案主体和后端服务主体应保持一致或具有清晰授权关系。
- 不要先用个人主体上线，再假设以后可以无成本迁移全部能力。

### 3.2 明确 Cat-AI 的产品定位

建议定位：

> 宠物工具 / 宠物信息管理 / 猫咪品种辅助识别 / 科普知识查询。

避免宣传为：

- 兽医诊断；
- 在线医疗；
- 疾病确诊；
- 药物处方；
- 保证准确的身份认证。

界面中应持续显示：

- “AI 识别结果仅供参考”；
- “健康观察不能替代执业兽医诊断”；
- “AI 生成内容”或等效显著提示；
- 紧急情况联系正规宠物医院的提示。

服务类目必须根据上线时微信后台的最新目录选择。若类目边界不清，应在开发前向平台确认，不要等代码完成后才发现需要额外资质。

### 3.3 功能范围分级

首版建议只做：

1. 微信登录或静默身份建立；
2. 拍照/相册选择一张猫咪图片；
3. AI 品种与外观辅助识别；
4. 本地知识库搜索；
5. AI 知识问答；
6. 猫咪档案和疫苗、驱虫、体重记录；
7. 数据删除与账号注销入口；
8. 隐私政策、用户协议、备案信息和 AI 提示。

后续再做：

- 同一只猫的个体识别；
- 多猫 Top-3 候选；
- 识别纠错反馈；
- 多设备同步；
- 家庭成员共享档案；
- 消息订阅和疫苗提醒。

## 4. 账号注册和后台准备

### 4.1 注册小程序

1. 进入[微信公众平台](https://mp.weixin.qq.com/)。
2. 选择注册“小程序”。
3. 使用未被其他公众平台账号占用的邮箱，按页面流程验证。
4. 选择并提交主体类型及证明材料。
5. 绑定管理员微信和联系方式。
6. 完成平台要求的主体认证或验证。
7. 在“开发管理/开发设置”取得 AppID。

不要把以下信息提交到 Git：

- AppSecret；
- 代码上传私钥；
- AI 供应商 Key；
- 云服务永久密钥；
- 管理员凭据。

### 4.2 配置基本信息

- 小程序名称；
- 简称；
- 头像；
- 简介；
- 服务类目；
- 客服方式；
- 管理员、开发者和体验成员；
- 隐私保护指引；
- 用户协议；
- 备案信息；
- 服务器域名。

名称、简介、页面功能和服务类目必须一致。不要在介绍中写有医疗诊断、百分百识别等无法兑现或可能触发资质要求的内容。

### 4.3 完成小程序备案

一般操作入口位于微信公众平台的小程序备案模块，流程通常包括：

1. 验证主体；
2. 填写主体负责人信息；
3. 填写小程序负责人和应用信息；
4. 上传证件、承诺书和必要的前置审批材料；
5. 平台初核；
6. 按通知完成短信核验；
7. 由属地通信管理局审核；
8. 获得备案编号并按平台要求展示。

工信部备案登记表显示，小程序、快应用的部分域名、公钥/MD5和网络接入字段可不填写；但小程序实际调用的业务后端仍要满足相应的域名、网络和服务器合规要求。

### 4.4 服务类目和资质

提交前核对：

- 功能是否与服务类目一致；
- 是否包含医疗、药品、新闻、教育、金融、直播、社交等受限能力；
- 是否需要前置审批文件；
- 主体经营范围是否能解释实际业务；
- 审核人员能否在体验账号下访问完整核心流程。

Cat-AI 首版应把“健康观察”控制在宠物科普和风险提醒，不提供诊断、处方或在线问诊。

## 6. 技术选型

| 方案 | 优点 | 缺点 | Cat-AI 建议 |
| --- | --- | --- | --- |
| 原生 WXML/WXSS/JS | 平台兼容最好、包较小、审核风险低 | 前端需重写 | 推荐 |
| Taro/uni-app | 多端复用、组件生态较多 | 构建层复杂、平台差异仍需处理 | 后续需要多端统一时考虑 |
| `<web-view>` 套现有网页 | 初期代码少 | 业务域名、体验、登录、审核和能力限制多 | 不推荐作为主应用 |
| 小程序直接请求模型 API | 实现看似简单 | Key 可被提取、无法安全限额和隔离 | 禁止 |
| 原生小程序 + FastAPI | 最大化复用现有后端 | 需自己部署、鉴权、数据库和运维 | 可行，推荐基线 |
| 原生小程序 + CloudBase | 微信身份、云函数、数据库、存储结合紧密 | 需要迁移服务和熟悉云平台 | 推荐生产方案之一 |

### 推荐架构

```text
微信小程序
  ├─ WXML/WXSS 页面
  ├─ wx.login / 会话 Token
  ├─ wx.chooseMedia / wx.uploadFile
  └─ 本地轻量缓存
          │ HTTPS / 云调用
          ▼
API 网关或云托管 FastAPI
  ├─ 微信登录换取服务端会话
  ├─ 用户、设备和额度隔离
  ├─ 图片校验、压缩、内容安全
  ├─ MiniMax/Kimi 服务端代理
  ├─ 知识库检索
  ├─ 猫咪个体 Re-ID 推理
  └─ 审计、限流、异常监控
          │
          ├─ 数据库：用户/宠物/记录/反馈
          ├─ 对象存储：原图/缩略图
          └─ Secret 管理：模型 Key/AppSecret
```

## 7. Cat-AI 必须修改的技术问题

### 7.1 API Key

当前 Android 构建会把选定模型 Key 混淆后放入 APK。小程序不能沿用这个做法：

- 小程序代码和网络请求都可能被分析；
- 混淆、Base64、拆分字符串都不能保护长期密钥；
- 供应商 Key 只能存放在服务端 Secret/环境变量；
- 服务端必须做用户额度、IP/账号限流、熔断和账单告警；
- 建议给小程序使用独立、低额度、可轮换的供应商子 Key。

### 7.2 用户登录

推荐流程：

1. 小程序调用 `wx.login()` 获取临时 code；
2. 将 code 发到 Cat-AI 后端；
3. 后端使用 AppID/AppSecret 与微信服务端换取用户标识和会话信息；
4. 后端创建自己的短期访问 Token；
5. 后续 API 使用 Cat-AI Token；
6. 服务端从 Token 确定 `user_id`，不接受客户端任意传入的 OpenID。

需要提供：

- Token 到期和刷新；
- 注销；
- 删除个人数据；
- 多设备会话管理；
- 失败重试和风控。

### 7.3 数据存储

当前 FastAPI 使用全局 `data/pets.json`，不具备多用户隔离。应迁移为数据库：

```text
users
  id, wechat_openid_hash, status, created_at

pets
  id, user_id, name, breed, appearance, notes, created_at, updated_at

pet_records
  id, pet_id, user_id, kind, record_json, occurred_at

pet_photos
  id, pet_id, user_id, object_key, thumbnail_key, purpose, created_at

identity_templates
  id, pet_id, user_id, model_version, vector, source_photo_id

identity_match_events
  id, user_id, predicted_pet_id, confirmed_pet_id, score, feedback
```

所有查询必须同时包含 `user_id` 条件。对象存储使用私有桶和短期签名 URL，不能把上传目录作为公开静态目录长期暴露。

### 7.4 图片上传

小程序端流程：

1. `wx.chooseMedia` 选择照片或调用相机；
2. 在客户端检查文件类型和大小；
3. 必要时压缩；
4. 使用 `wx.uploadFile` 上传到后端或私有对象存储；
5. 服务端重新检查 MIME、魔数、尺寸和像素总量；
6. 删除 EXIF 中不需要的位置等元数据；
7. 生成缩略图；
8. 执行识别；
9. 按用户选择决定是否长期保存原图。

不能只相信文件扩展名。必须限制解码像素，防止超大图片导致内存耗尽。

### 7.5 知识库

现有知识库约 52 KB，可采用双层方案：

- 小程序包内放精简、结构化 JSON，用于快速基础查询；
- 服务端保留完整 Markdown 检索、引用排序和 AI 问答；
- 回答返回 `answer + citations + model_used + generated=true`；
- UI 显示来源和“AI 生成，仅供参考”；
- 健康问题优先展示紧急就医规则。

### 7.6 猫咪个体识别

不建议把当前约 89 MB 的 ONNX 模型放入小程序代码包。推荐：

```text
用户上传照片
  → 服务端质量检测/猫主体裁剪
  → ONNX Runtime 服务端生成 512 维向量
  → 仅匹配当前 user_id 的猫咪模板
  → 返回 Top-3 与分数
  → 用户确认“正确/错误/新猫”
  → 保存反馈和新模板
```

正式上线前仍需真实跨时间数据校准阈值；不得把桌面 POC 的演示阈值直接用于用户判断。

## 8. 后端 API 建议

建议新增版本化 API：

```text
POST   /api/v1/auth/wechat
POST   /api/v1/auth/refresh
POST   /api/v1/auth/logout
DELETE /api/v1/account

GET    /api/v1/models
POST   /api/v1/identify
POST   /api/v1/identity/match
POST   /api/v1/identity/feedback

GET    /api/v1/pets
POST   /api/v1/pets
GET    /api/v1/pets/{id}
PATCH  /api/v1/pets/{id}
DELETE /api/v1/pets/{id}
POST   /api/v1/pets/{id}/records
DELETE /api/v1/pets/{id}/records/{record_id}

POST   /api/v1/knowledge/search
POST   /api/v1/knowledge/ask

GET    /api/v1/privacy/export
DELETE /api/v1/privacy/photos/{id}
```

统一要求：

- JSON 错误结构和稳定错误码；
- 请求 ID；
- Token 鉴权；
- 用户级限流；
- 上传大小和像素限制；
- 幂等键；
- 审计日志；
- AI 超时、重试和熔断；
- 敏感字段不写日志；
- API Key 不返回客户端。

## 9. 网络与域名配置

小程序正式环境不能依赖开发工具中的“不校验合法域名”。需要在微信公众平台配置实际使用的：

- `request` 合法域名；
- `uploadFile` 合法域名；
- `downloadFile` 合法域名；
- `socket` 合法域名（如使用 WebSocket）。

上线检查：

- 全链路 HTTPS；
- 证书有效，域名完整匹配；
- 不使用裸 IP；
- 不依赖任意端口；
- 域名和服务器备案符合要求；
- 测试/生产域名隔离；
- CORS 不能代替鉴权；
- 后端拒绝未认证请求；
- 上传和下载 URL 具有有效期。

## 10. 隐私与安全

### 10.1 数据清单

Cat-AI 可能处理：

- 微信侧用户标识；
- 猫咪照片；
- 相册或相机选择的临时文件；
- 猫咪姓名、品种、生日、体重；
- 疫苗、驱虫和健康备注；
- AI 问题和回答；
- 设备、日志和安全风控信息。

### 10.2 隐私保护指引

隐私指引必须与实际代码使用的接口一致，至少说明：

- 收集什么；
- 为什么收集；
- 使用和保存多久；
- 是否传给 AI 模型服务商；
- 如何删除、导出和注销；
- 联系方式；
- 未成年人相关安排；
- 第三方 SDK 清单。

涉及隐私接口时，应按平台要求在调用前完成用户告知和同意。不能用“不同意就完全不能进入应用”的方式强迫授权非必要权限；应在用户触发拍照或上传时再申请。

### 10.3 AI 合规

- 显示 AI 生成提示；
- 明确结果可能错误；
- 对输入和输出做内容安全处理；
- 不输出危险药物剂量或替代诊断；
- 保存模型、提示词和知识库版本，便于追溯；
- 提供投诉、纠错和删除入口；
- 与模型供应商确认面向中国公众提供服务时的合规责任和数据处理条款；
- 如允许用户公开传播 AI 生成内容，应进一步落实生成合成内容标识要求。

## 11. 页面迁移对应表

| 当前能力 | 小程序页面/组件 | 后端变化 |
| --- | --- | --- |
| 首页上传识别 | `pages/identify` | 鉴权上传、额度、对象存储 |
| 模型选择 | 设置或隐藏为服务端策略 | 不返回 Key，只返回可用模型标签 |
| 品种知识 | `pages/knowledge` | 精简本地 JSON + 服务端检索 |
| AI 问答 | 问答组件 | 鉴权、限流、引用与 AI 标识 |
| 宠物列表 | `pages/pets` | 按 `user_id` 查询 |
| 宠物详情 | `pages/pet-detail` | 所有权校验 |
| 健康记录 | 详情页分区 | 数据库子记录 |
| 重新识别 | 详情页上传组件 | 私有图片、事务更新 |
| Android SQLite | 不直接迁移 | 可提供手工导入/账号同步方案 |
| 个体识别 | Top-3 候选组件 | 服务端 ONNX 和模板库 |

现有 Android 本地档案不会自动出现在微信小程序。若需要迁移，可设计：

- Android 登录同一 Cat-AI 账号后上传；
- Android 导出加密 JSON/二维码，小程序确认导入；
- 暂不迁移，由用户重新建档。

不建议通过公开链接暴露健康档案。

## 12. 开发、测试、审核和发布

### 12.1 开发版

- 编译和模拟器运行；
- 检查 WXML/WXSS；
- Mock 后端；
- 开发环境 AppID/云环境；
- 开发者工具 Network、Storage、Console 调试。

### 12.2 体验版

- 上传开发版本；
- 设置体验版；
- 添加体验成员；
- 使用真实微信账号和真机测试；
- 配置体验版隐私指引；
- 测试实际合法域名、相机、相册、弱网和后台恢复。

### 12.3 提交审核材料

通常需要准备：

- 版本说明；
- 功能页面和服务类目；
- 测试账号或可复现路径；
- 核心功能截图；
- 隐私保护指引；
- 用户协议；
- 备案信息；
- 所需行业资质；
- 如功能需要，审核说明或演示视频；
- AI 功能说明、免责声明和数据用途说明。

### 12.4 审核前自检

- 不存在空白页、死按钮和占位文字；
- 审核人员无需联系客服才能体验；
- 类目与功能一致；
- 无诱导关注、诱导分享；
- 不强制获取非必要个人信息；
- 相机/相册拒绝授权后有可理解的提示；
- 账号注销和数据删除可找到；
- AI 回答有来源和风险提示；
- 断网、超时、429、服务不可用有友好反馈；
- 服务端没有公开 Key；
- 备案、隐私和主体名称一致。

### 12.5 发布

1. 微信开发者工具上传代码；
2. 在公众平台版本管理选择开发版本；
3. 提交审核并填写材料；
4. 根据反馈整改；
5. 审核通过后主动发布；
6. 观察错误率、AI 成本和用户反馈；
7. 如平台提供灰度能力，先小范围验证；
8. 保留上一个稳定版本的回滚方案。

### 12.6 CI/CD

可使用 `miniprogram-ci` 自动执行预览和上传。官方 npm 包说明需要在公众平台下载代码上传密钥并配置 IP 白名单。

安全要求：

- 私钥只放 CI Secret；
- 禁止提交仓库；
- 限制构建机 IP；
- 区分体验和生产环境；
- 自动生成版本号和变更说明；
- 上传前执行包体、敏感字符串和接口域名检查。

- iOS/Android 微信；
- 不同屏幕和字体缩放；
- 深色模式；
- 低端设备；
- 不同基础库版本；

- 权限拒绝；
- 备案号；
- AI 标识；
- 免责声明；
- 类目一致；
- 体验账号；

| 1 | 后端鉴权、数据库、用户隔离、限流 | 5～10 天 |
| 2 | 原生小程序 UI 与基础组件 | 7～12 天 |

## 15. 风险评估

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| API Key 泄漏 | 极高 | Key 仅放服务端 Secret，客户端令牌化 |
| 多用户互读档案 | 极高 | 数据库强制 `user_id`、对象级授权测试 |
| AI 费用被滥用 | 高 | 用户额度、限流、验证码/风控、账单告警 |
| 照片和健康信息泄漏 | 高 | 私有存储、短期 URL、删除与留存策略 |
| 类目/资质不匹配 | 高 | 开发前确认，审核材料与实际功能一致 |
| 隐私接口未声明 | 高 | 接口清单与平台隐私指引逐项对齐 |
| AI 健康误导 | 高 | 不诊断、来源引用、免责声明、紧急提示 |
| 模型放入小程序导致包体/性能失败 | 高 | 服务端推理 |
| 备案拖延 | 中高 | 与开发并行启动，预留管局审核时间 |
| 审核环境无法使用 | 中 | 提供体验路径、测试账号、演示说明 |
| Android 档案无法同步 | 中 | 设计账号同步或明确首版不迁移 |

## 16. 上线验收门槛

- 小程序备案完成；
- 类目和必要资质完成；
- 隐私指引与代码实际调用一致；
- 所有生产域名和 HTTPS 有效；
- 客户端包内搜索不到任何 AI Key/AppSecret；
- 未登录和越权访问测试全部失败；
- 每个用户只能读写自己的宠物；
- 图片上传限制、内容安全和删除生效；
- AI 问答有生成提示、来源和健康免责声明；
- MiniMax/Kimi 失败时可降级；
- 真机核心流程通过；
- 断网、超时、429、5xx 有用户反馈；
- 错误监控、费用告警和回滚方案就绪；
- 审核材料可完整复现功能。

## 17. 推荐执行顺序

立即执行：

1. 确定企业/个体/个人主体；
2. 注册小程序并取得 AppID；
3. 在后台确认 Cat-AI 可用服务类目；
4. 同时启动小程序备案；
5. 准备备案、隐私、用户协议和 AI 免责声明；
6. 新建 `miniapp/` 原生项目；
7. 先改造后端鉴权与用户隔离；
8. 再迁移识别、知识库和档案页面；
9. 建体验版并进行真机测试；
10. 提交审核，按反馈迭代。

技术优先级：

```text
服务端 Key 与鉴权
  > 用户数据隔离
  > 图片安全与对象存储
  > 小程序页面迁移
  > 隐私和 AI 提示
  > 体验版测试
  > 个体识别
```

最终建议：批准“小程序账号/备案准备 + 后端安全改造 + 原生小程序骨架”三个工作流并行启动。不要在无鉴权的现有 FastAPI 上直接接入公开小程序，也不要为了快速上线把供应商 API Key 放入小程序代码。
