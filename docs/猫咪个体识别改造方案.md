# Cat-AI 猫咪个体识别与交互反馈改造方案

> 版本：1.0  
> 日期：2026-08-21  
> 适用代码基线：Cat-AI Android/Web 1.0.2

> 更新说明（2026-08-27）：本文保留为 Android/本地优先的历史设计。涉及微信小程序联机共享、开放集 FPIR/FNIR、CloudBase 数据层、社区投票和可回滚身份簇时，以[《同猫识别技术路径实施方案（联机版）》](./同猫识别技术路径实施方案.md)为当前基线；本文中的少量样本阈值不得直接用于生产。

## 1. 执行摘要

建议引入“猫咪个体识别”，但产品名称应使用“身份匹配”“可能是同一只猫”，不能宣传为绝对身份认证。该功能应与现有“品种识别”分开：品种识别回答“是什么品种”，个体识别回答“是否是用户档案里的团子”。

推荐技术路线不是让 MiniMax/Kimi 直接比较两张照片，而是使用专门的动物 Re-ID 特征模型，在设备端生成向量并做余弦相似度匹配；大模型只负责解释结果、引导补拍和生成文字说明，不参与最终身份判定。

综合结论：

- “多猫家庭辅助区分”可行性：高，约 8/10。
- “同一只猫验证 + 用户确认”可行性：高，约 8/10。
- “完全自动、无需确认的身份认证”可行性：低，约 4/10。
- Android 端离线推理可行性：中高，约 7/10。
- 直接使用研究模型公开分发的许可可行性：低，必须逐项审查。
- 推荐首选候选：Apache-2.0 的 `open-noodle/pet-recognition-small`，先做 POC，不直接承诺生产效果。

## 2. 当前项目约束

当前项目具备以下基础：

- FastAPI 后端负责 Web API、知识库、品种识别和档案。
- Android 是纯 Java WebView，使用 `AndroidBridge` 承接图片、AI 和本地搜索。
- Android 档案目前保存在 WebView `localStorage`。
- Android 最低版本 API 24、目标版本 API 35。
- MiniMax 与 Kimi APK 使用相同应用包名，仅模型供应商不同。
- 当前 APK 约 126 KB；加入推理运行时和视觉模型后体积会显著增长。
- 当前公网后端没有账户、设备隔离和可靠鉴权，因此不适合直接托管多用户身份向量。

个体识别需要长期保存多张参考图、特征向量和用户确认记录，继续依赖 `localStorage` 会增加数据丢失和迁移风险。因此正式接入前，应先增加 Android 原生数据库层。

## 3. 资料与可借鉴结论

### 3.1 研究依据

1. [Pet Cat Face Verification and Identification](https://cs230.stanford.edu/projects_fall_2019/reports/26251543.pdf)

   使用猫脸检测、EfficientNet 和 Triplet Loss 生成 64 维特征。报告约 95% 验证准确率，但开放集 Rank-5 识别约 81%。说明“同猫验证”比“从大量未知猫中自动识别”更成熟。

2. [PetFace: A Large-Scale Dataset and Benchmark for Animal Identification](https://arxiv.org/abs/2407.13555)

   覆盖 13 类动物、25 万以上个体，系统评估 ArcFace 等个体识别方法。适合作为训练、验证协议和指标设计参考。

3. [PetFace 官方代码](https://github.com/mapooon/PetFace)

   提供猫类 ArcFace 训练、Verification、Re-identification 和对齐流程。但仓库、数据集和预训练模型明确限非商业研究，不能直接放入公开或商业 APK。

4. [CatFLW](https://arxiv.org/abs/2305.04232)

   提供自然环境猫脸框与 48 个猫脸关键点，可参考猫脸质量检查和姿态对齐。官方数据采用 CC BY-NC 4.0，不适合直接用于商业训练成果发布，除非单独确认授权。

5. [WildlifeDatasets](https://openaccess.thecvf.com/content/WACV2024/papers/Cermak_WildlifeDatasets_An_Open-Source_Toolkit_for_Animal_Re-Identification_WACV_2024_paper.pdf)

   可参考动物 Re-ID 的数据拆分、Triplet/ArcFace 基线和跨个体评测方式。

### 3.2 可运行实现

1. [NekoNet](https://github.com/tokudayo/NekoNet)

   提供猫脸 YOLOv5 检测器和 EfficientNetV2-B0 128 维 ONNX 特征模型，仓库报告验证准确率约 96.2%。优点是模型约 6M 参数、适合移动端 POC；缺点是仓库没有清晰的可分发许可证，数据也来自 Petfinder 抓取，只能作为技术参考，不能在未确认授权前直接发布。

2. [open-noodle/pet-recognition-small](https://huggingface.co/open-noodle/pet-recognition-small)

   Apache-2.0，DINOv2-small 约 22M 参数，输出 512 维 L2 归一化向量，输入为 224×224 RGB，使用余弦相似度匹配。模型卡报告猫测试集 Top-1 约 0.913、AUC 约 0.986，并说明训练数据采用 CC0/CC BY。它识别的是整只动物裁剪，不只依赖猫脸，更适合花纹明显的猫。

3. [open-noodle/pet-recognition-large](https://huggingface.co/open-noodle/pet-recognition-large)

   大模型约 300M 参数，不适合当前 APK 首版。可作为服务端或效果上限对照，不推荐直接嵌入手机。

### 3.3 移动端推理

1. [ONNX Runtime Mobile 官方指南](https://onnxruntime.ai/docs/tutorials/mobile/)

   Android Java 可以直接使用 `onnxruntime-android`。官方建议量化模型优先从 CPU 开始，非量化模型优先测试 XNNPACK；NNAPI 是否更快取决于设备和算子支持。

2. [ONNX Runtime Android 构建说明](https://onnxruntime.ai/docs/build/android.html)

   R8 压缩时需要保留 ONNX Runtime 相关类，否则 Release 可能在运行时崩溃。

3. [ORT 格式与移动优化](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html)

   可将 ONNX 转成 ORT 格式并裁剪运行时算子。INT8 权重量化理论上可将权重体积降到 FP32 的约四分之一，但必须重新验证精度和设备性能。

## 4. 技术路线比较

| 路线 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| MiniMax/Kimi 两图比较 | 开发最快，不需要本地模型 | 无稳定阈值、成本高、结果不可重复、模型会过度自信 | 只可作为解释或补充信号 |
| NekoNet 猫脸 ONNX | 小、速度快、针对猫脸 | 授权不清晰；对侧脸、遮挡、纯色同窝猫有限 | 仅用于内部 POC |
| PetFace ArcFace | 研究基础强、评测完整 | 官方数据和权重限非商业 | 用于方法和评测参考 |
| open-noodle small | Apache-2.0、已有 ONNX、整猫特征、移动端规模可接受 | 第三方模型；需自行复测中国家庭猫场景 | 推荐首选 POC |
| 自建商业可用模型 | 授权和效果完全可控 | 数据、标注、GPU 和训练成本高 | 中长期生产路线 |
| 服务端推理 | APK 小、模型可快速升级 | 需要账号、鉴权、GPU、隐私与持续成本 | 用户规模扩大后再做 |

## 5. 推荐总体架构

```text
用户拍照/选择图片
       ↓
图片质量检查（亮度、模糊、尺寸、猫数量）
       ↓
猫主体检测或用户辅助裁剪
       ↓
224×224 RGB 归一化
       ↓
ONNX Re-ID 模型生成 512 维 L2 向量
       ↓
与本机每只猫的多个身份模板计算余弦相似度
       ↓
高相似 / 不确定 / 低相似 + Top-3 候选
       ↓
用户确认“是同一只 / 不是 / 不确定”
       ↓
更新模板、档案和匹配反馈
```

模型不应直接输出猫咪 ID。模型只输出与身份无关的特征向量，应用通过本地图库完成匹配。

## 6. 产品流程

### 6.1 身份建档

每只猫至少采集 3 张、建议 5 张参考图：

- 正脸。
- 左侧或右侧脸。
- 全身侧面。
- 能清楚看到特殊斑纹的位置。
- 不同光线下的一张补充照片。

每张图片先做质量检查；不合格照片不进入身份模板。每只猫保存多个向量，不只保存平均向量，以适应正脸、侧脸和全身差异。

### 6.2 新照片匹配

上传照片后显示：

```text
这只猫可能是「团子」
匹配等级：较高

其他候选：
1. 豆包（中等）
2. 花花（较低）

[是团子] [不是，创建新档案] [暂不确定]
```

不得自动合并档案。即使相似度很高，也由用户确认；只有用户多次确认后，才允许提供“自动选中但仍可撤销”的体验。

### 6.3 反馈闭环

每次确认保存：

- 查询照片或其受控缩略图。
- Top-3 候选和原始相似度。
- 用户最终选择。
- 模型版本、裁剪方式、图片质量。
- 是否把新向量加入模板。

“不是同一只”的负反馈与“是同一只”的正反馈同样重要，可用于设备级阈值校准和后续模型评估。

## 7. 数据层改造

### 7.1 从 localStorage 迁移

正式实现前，将 Android 档案迁移到 Room/SQLite。Java WebView 仍可通过 `AndroidBridge` 使用 JSON 契约，不需要立即重写前端。

建议实体：

```text
Pet
- id
- name
- breed
- profile fields...

PetPhoto
- id
- pet_id
- local_path
- thumbnail_path
- capture_time
- quality_score
- view_type

IdentityTemplate
- id
- pet_id
- photo_id
- model_version
- embedding_blob
- embedding_dimension
- crop_type
- quality_score
- created_at
- active

IdentityMatchEvent
- id
- query_photo_id
- candidate_pet_id
- similarity
- rank
- decision: confirmed / rejected / uncertain
- model_version
- created_at
```

512 维 `float32` 向量约 2 KB；即使每只猫保存 10 个模板，向量本身体积也很小。主要存储压力来自原图，应使用应用私有文件目录保存压缩图，并允许用户删除原图、仅保留模板。

### 7.2 数据迁移

首次升级时：

1. 读取 `cat_ai_android_pets_v1`。
2. 写入 Room/SQLite。
3. 校验猫数量、ID 和图片。
4. 写入迁移完成标记。
5. 保留旧数据一个版本周期，确认成功后再清理。

## 9. 模型推理设计

### 9.1 首版模型

POC 使用 `pet-recognition-small`：

- 输入：`float32 [1, 3, 224, 224]`。
- 颜色：RGB。
- 归一化：ImageNet mean/std。
- 输出：512 维 L2 归一化向量。
- 距离：余弦相似度，等价于归一化向量点积。

模型卡指标不能直接当作本项目准确率。必须使用真实家庭猫照片重新评测，尤其包括：纯黑猫、纯白猫、同窝猫、幼猫成长、长毛遮挡、侧脸、夜间和多人多猫场景。

### 9.2 猫主体裁剪

第一阶段可要求“一张照片只拍一只猫”，并提供用户可调整裁剪框。这样可以先验证 Re-ID 模型，避免同时引入检测器造成问题定位困难。

第二阶段再增加轻量猫检测器：

- 检测到 0 只猫：提示重新拍摄。
- 检测到 1 只猫：自动裁剪并预览。
- 检测到多只猫：要求用户点选目标猫。

检测器必须单独审查模型权重和训练数据许可。

### 9.3 模板匹配

每只猫保留多个高质量模板。候选分数建议使用：

```text
最终分数 = 0.6 × 最相似模板 + 0.4 × Top-3 模板平均值
```

这比只与平均向量比较更能适应侧脸和全身差异。低质量模板、重复模板和长期被否定的模板应降权或停用。

### 9.4 阈值

禁止直接把余弦相似度显示成“身份概率”。阈值必须通过本项目数据校准：

- 高阈值：在不同猫误认率 FAR ≤ 1% 的条件下选择。
- 低阈值：在同猫拒绝率可接受的条件下选择。
- 两阈值之间统一显示“不确定，请人工确认”。

在完成实测前，不在产品代码中写死所谓通用 80%/90% 阈值。

## 10. 图片质量与交互反馈

质量检查至少包含：

- 最短边尺寸。
- 拉普拉斯方差或其他模糊指标。
- 平均亮度与过曝比例。
- 猫主体占画面比例。
- 是否出现多只猫。
- 裁剪后是否缺少头部或主要花纹。

向用户展示具体原因：

- “照片较暗，请靠近光源重拍。”
- “猫咪在画面中太小，请靠近一些。”
- “检测到多只猫，请点选要识别的猫。”
- “本次角度与参考图差异较大，结果仅供参考。”

匹配结果同时提供“有帮助/没帮助”和“实际是哪只猫”的反馈入口。

## 11. 模型打包策略

### 11.1 随 APK 打包

优点：完全离线、安装后立即可用。缺点：APK 从约 126 KB 增长到数十 MB，模型升级必须发布新 APK。

适合首个内部 POC。

### 11.2 首次使用时下载

主 APK 保持较小，用户开启“个体识别”后下载模型到应用私有目录。下载必须：

- 使用 HTTPS。
- 固定版本和 SHA-256。
- 支持断点或失败重试。
- 下载完成后原子替换。
- 设置中显示模型版本和占用空间。

适合后续公开侧载版本。应用商店版本可进一步考虑动态交付。

### 11.3 量化

先用 FP32 建立准确率基线，再测试 FP16/INT8。只有当 AUC、FAR、召回和不同手机延迟都满足要求时才切换，不能只因文件更小就直接量化发布。

## 12. Web 与服务端路径

首版只在 Android 本地运行个体识别，原因是：

- 当前后端宠物档案没有用户隔离。
- 当前 API 无完善鉴权。
- 服务端身份向量会成为敏感的长期标识数据。
- 服务端推理需要持续算力和隐私政策。

未来服务端版的前置条件：

1. 账号或设备身份。
2. 每用户数据隔离。
3. API 鉴权、限流和审计。
4. 图片和向量的删除、导出机制。
5. 数据保留期限和隐私说明。
6. 可轮换的服务端密钥，不再公开供应商 Key。

## 13. 测试与验收

### 13.1 数据集设计

POC 最少收集：

- 10～20 只猫。
- 每只 8～15 张照片。
- 至少 3 次不同时间拍摄。
- 包含同品种、同花色和同窝猫。
- 每只猫的训练参考图与测试图必须来自不同拍摄批次。

Beta 阶段建议扩大到 50 只以上。不能把同一连拍序列随机拆到训练和测试两边，否则指标会虚高。

### 13.2 指标

- Verification ROC AUC。
- EER。
- TAR @ FAR=1%。
- Top-1、Top-3 Identification。
- 未知猫拒绝率。
- 同窝/同花色子集指标。
- 图片质量拒绝率。
- 单次推理 P50/P95 延迟。
- 峰值内存、安装包体积、电量消耗。
- 用户确认率、纠正率和“不确定”比例。

### 13.3 首版验收标准

- 单只猫建档至少支持 3 个模板。
- 20 只猫测试集 Top-3 ≥ 90%。
- 不同猫 FAR ≤ 1% 时，同猫召回达到可接受水平并记录实际值。
- 中档 Android 设备单次向量生成目标 ≤ 2 秒。
- 无网络时能够完成匹配。
- 所有匹配都允许人工修改和撤销。
- 清除某只猫档案时，其照片、模板和反馈全部删除。
- Release + R8 构建无 ONNX Runtime 崩溃。

Top-3 指标仅适用于辅助候选选择，不能替代 FAR/FRR 验证指标。

## 14. 隐私与安全

- 默认所有身份模板和照片只保存在设备端。
- 特征向量应视为敏感标识数据，不写入日志或崩溃报告。
- 不把照片或向量发送给 MiniMax/Kimi做身份判定。
- 用户能够查看、导出和删除全部身份数据。
- 卸载或清除应用数据前明确提示档案会丢失。
- 数据备份必须由用户主动开启，并说明备份位置。
- 若未来云同步，必须单独同意，不和普通 AI 问答授权混在一起。

## 15. 分阶段实施计划

### 阶段 0：技术 POC，2～4 天

- 在电脑端下载候选 ONNX 模型。
- 建立 10～20 只猫的小型跨拍摄批次测试集。
- 验证输入输出、余弦相似度和基础指标。
- 测量模型大小、FP32/FP16/INT8 差异。
- 输出“继续/停止/更换模型”结论。

不改正式 UI，不发布 APK。

### 阶段 1：数据基础，3～5 天

- 引入 Room/SQLite。
- 迁移现有 localStorage 档案。
- 增加照片、模板和反馈表。
- 增加 JSON 导入导出。

### 阶段 2：Android MVP，5～8 天

- 集成 ONNX Runtime。
- 用户辅助裁剪。
- 身份建档与向量生成。
- Top-3 匹配。
- 用户确认和反馈。
- 设备端性能测试。

### 阶段 3：交互完善，4～7 天

- 图片质量提示。
- 多模板管理。
- 匹配历史和撤销。
- 不确定区间。
- 档案页展示身份模型状态。

### 阶段 4：自动检测与 Beta，1～3 周

- 选择并审查猫检测模型。
- 多猫点选。
- 扩大测试数据。
- 校准阈值。
- 灰度收集匿名指标和用户反馈。

以上是单开发者、复用现有 Java/WebView 架构的粗略估算，不包含自训练模型和云端账号系统。

## 16. 可行性评估

| 维度 | 评级 | 说明 |
|---|---|---|
| 产品价值 | 高 | 多猫家庭、防重复建档、照片自动归档价值明确 |
| 算法可行性 | 中高 | Verification 可用；完全开放集识别仍有明显误差 |
| Android 集成 | 中高 | 现有 Java Bridge 可扩展，ONNX Runtime 有官方 Android 支持 |
| 低端设备性能 | 中 | 需量化、裁剪模型并实机测试 |
| 数据存储 | 中 | 必须先从 localStorage 迁移 |
| 隐私 | 高可控 | 本地推理可避免上传身份数据 |
| 模型许可 | 中低 | 多个优秀研究资源限非商业或授权不清 |
| 维护成本 | 中 | 模型版本、阈值和数据库迁移都需要持续管理 |

最终建议：批准阶段 0 POC 和阶段 1 数据迁移；阶段 2 是否进入正式 APK，以 POC 的跨拍摄测试、许可证复核和移动端性能结果为门槛。

## 17. 明确不采用的做法

- 不把供应商大模型回答当作身份真值。
- 不只拍一张参考照片就开启自动识别。
- 不把相似度直接显示为真实概率。
- 不在没有用户确认的情况下合并猫咪档案。
- 不直接分发 PetFace、CatFLW 或授权不清的 NekoNet 权重。
- 不在当前无用户隔离的 FastAPI 中保存多用户身份向量。
- 不先加入大型检测模型和复杂训练流水线再验证核心 Re-ID 是否有效。

## 18. 下一步决策清单

进入开发前需要确认：

1. 产品是否仅面向个人侧载，还是计划公开/商业分发。
2. 首版能否接受用户辅助裁剪和至少 3 张参考照片。
3. 是否允许 APK 增长数十 MB，或必须采用模型首次下载。
4. 是否先完成 Room/SQLite 迁移。
5. 是否有 10～20 只猫的多时段照片用于 POC。
6. 是否接受“辅助匹配 + 人工确认”，而不是绝对身份认证。

满足上述条件后，推荐从 `pet-recognition-small + ONNX Runtime Android + Room/SQLite + Top-3 人工确认` 开始验证。
