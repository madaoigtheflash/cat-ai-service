# 对话收敛版：三轮实现与体验报告

日期：2026-09-30。分支：codex/cat-companion-convergence-20260930。

参考：[既有CATO调研](../CATO-功能设计与UI风格调研-2026-09-29.md)与上一轮实验。借用的是“对话捕捉意图、结构化确认、历史可回看”的产品思路，不声称取得CATO内部代码或完整设计规范；原调研未验证的界面细节也不作为事实。

## 结论

从“社交信息流首页”收敛为“虚拟猫对话入口 → 确认卡 → 真实本机记录”，社区仍保留，但不再抢占主线。
这是一份开发自测/独立代码及界面审阅报告，不是用户访谈结果，不代表产品已上线。原工作目录与生产云端没有部署、迁移或删除。

### 已形成的框架

| 层级 | 实际实现 | 边界 |
|---|---|---|
| 聊聊 | 虚拟猫小桃、本地规则引导、可选云端文字适配器、草稿保存、失败重试 | 默认不是自由生成对话；云端源码默认关闭且未部署 |
| 照片 | 相机/相册选择 → 本机预览 → 主动上传观察 → 可编辑登记卡 | 复用 identifyCat；本轮未发送真实照片，不证明识别准确率 |
| 登记 | 明确句式与按钮生成草稿，确认后用原 storage 写入猫档案 | 疑问、否定、同名不猜测；不自动合并同猫 |
| 关系 | 起点猫、终点猫、双方身份；母子、父子、照护、朋友、玩伴 | 本机身份记录与云端方向投票不互转，亲缘不是图片判定 |
| 地图 | 主动选点 → 立即粗化 → 本机地图和等价文字列表 | 约2公里网格中心；不记录精确点，不自动同步成云端热图 |
| 社区 | 猫友广场、我的动态、主动分享编辑器、原有评论与回应、小屋邀请 | 只复用原接口，不自动分享聊天、健康记录或位置；本轮无真实发布 |
| 自己的数据 | 本机猫档案、双方关系、粗位置、私人历史、确认回执、显式复制导出 | 不是管理员后台，也不是云端全量数据查询或跨设备备份 |

## 第1轮：先打通“说 → 确认 → 保存”

实现：一个待处理确认卡，复用真实 savePet/saveRelationship；聊天、草稿、回执与实体分开。本地解析只覆盖有限明确句式，未知表达回复说明而非假装理解。

验证：

- “登记猫咪叫奶糖”先出现草稿；不确认时猫档案数不变。
- “奶糖是不是团子的妈妈？”、“不要登记”等不创建动作。
- 重复确认不重复创建；取消普通草稿不写实体；同名档案、已存在关系及过期目标拒绝静默覆盖。
- 写入结果不确定时保留原请求；重试只核对已经存在的相同结果，不重建已删实体。

发现并修复：输入发送后清空字符串被存储读回逻辑误认成缺值，导致“已保存却报失败”。改为验证实际 JSON 快照，新增空草稿和默认时钟/ID集成回归。

体验判断：输入入口已经集中，但规则式语句远不能取代自由对话。需要在首屏明确“本地引导”，不能把这一轮称作大模型陪聊已完成。

## 第2轮：接回识猫、双方关系与地图

实现：直接复用图片观察服务；结果仅作可编辑建议。位置选择不会把系统返回的地址/门牌写入日志，只保留用户编辑的粗区域名称与已粗化坐标。真实猫咪头像与虚拟角色图标分离。

模拟器脚本用两只明确标为测试样本的猫：

1. 分别输入奶糖、团子并确认，生成两份本机档案。
2. 输入“奶糖是团子的妈妈”，确认母亲 → 孩子方向。
3. 使用模拟选点（不是设备定位）登记公园粗区域。
4. 查看本机历史、关系数与地图；结束后恢复本机测试前的数据键。

首轮渲染发现：

- 微信原生按钮默认宽度挤窄输入框、角色标题和小卡片。增加限定选择器，不改全局按钮。
- 地图只有一个点时 include-points 将视野放大到建筑范围；单点改用12级视野，多点才适配范围。
- 键盘高度状态下收起次要快捷动作，给输入和发送留空间；不把模拟高度当物理键盘验收。

体验判断：登记不再需要先找功能菜单；但“识别出的猫可能已经建档”仍需转到档案/既有同猫流程核对，未完成对话内的候选关联闭环。不能宣传为“一张图确定同猫”。

## 第3轮：真实回执、失败恢复与公开边界

修正：

- 历史保留原对话，并另外展示实际确认回执。旧消息说“待确认”不能被篡改成当时已保存；回执也不能证明实体当前仍存在。
- 不确定写入后点取消，显示“关闭待核对草稿，不撤销可能已保存记录”，引导本人核对。
- 云端失败重试锁定旧消息和上下文；用户新输入不会被成功回调清空。已经拿到回复但本机写失败时可重试保存，不重复请求供应商。
- 超长本机历史在发送前截短，避免某条旧消息永久阻塞后续短消息。
- 云端只返文字，不执行工具。补拦常见“已经登记/保存”的假操作表述；正则不是完整语义安全机制。
- 新云函数默认关闭，需要服务端显式启用和最多32个测试身份的精确名单；客户端伪造身份不能绕过。没有持久化额度/并发限流，仍是部署前阻断项。

体验判断：最重要的改进不是更多可爱装饰，而是让人知道“这是角色回复、这是草稿、这是已确认记录、这是公开分享”。当前状态表达仍偏说明性，需真实新用户验证是否读得懂。

## 下一轮应收敛到哪里

优先只验证一个问题：**一个人遇到猫后，能不能自然说一句话，并放心把它变成正确记录？**

1. **先补真实对话的小范围验证**：审核/隐私与第三方披露、测试身份、持久额度和并发限制先过门槛；再测10–20条真实任务表达。云端仍只提建议，不写实体。若用户仍把虚拟回复当保存成功，停止扩大开放，先改确认与回执。
2. **把已有猫关联做到同一条主线**：图片后提供“可能是这些猫 / 新猫 / 无法确定”，只能用户确认；引入真实合法样本评估误匹配和拒识，不根据图像相似度自动合并。
3. **少一张表单，而非多一个功能**：邀请3–5位用户完成登记、取消、关系方向、粗位置和主动分享。记录卡住的步数及错误，不以聊天时长、打卡或发帖量当成功标准。若副功能分散注意，将公共广场进一步折叠，不删小屋邀请与评论。

暂不加入：计时、账本、连续打卡、情绪评分、自动诊疗、公开精确位置、把私人历史自动发广场。上一轮实验分支保留供以后取用，不批量合并。

## 审阅顺序

先看首屏与登记确认卡，再看历史中的实际回执，最后看社区分享边界。请重点反馈：语气是否舒服、哪些说明太多、什么时候不知道下一步该点哪里，以及哪些内容绝对不想上传。
